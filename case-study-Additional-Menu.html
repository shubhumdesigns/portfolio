The Problem

Adding a menu meant writing code — every single time

Before this feature existed, adding a navigation menu to any property website required a designer or developer to write custom HTML or JavaScript by hand. One typo could break a live client site — and every update meant repeating the whole process from scratch.

No dedicated feature — manual code only

There was no built-in way to add or manage navigation menus. Every menu had to be hand-coded using custom HTML or JavaScript, making it inaccessible to non-technical users.

One typo could break a live client site

Custom code had no safety check. A single syntax error would go live immediately with no warning and no easy way to revert — putting client-facing sites at real risk.

Every update required going back into the code

Adding a link, changing a URL, reordering items — all of it meant opening the raw markup again. There was no visual editor, no safety, and no independence for non-technical team members.

Company-wide menus had no scalable solution

Clients with 100+ properties and shared links (e.g. a common Terms or Accessibility page) had no way to define one menu at the company level and apply it across properties. Every property had to be updated individually.

Before — The Old Way

How it was done before this feature existed

Designers and developers had two options: write a list manually inside an HTML Widget, or inject it via JavaScript directly in the Site Editor. Both required technical knowledge, and any mistake went live immediately on the client's website.

Method 1 — HTML Widget: A designer would open an HTML Widget and manually write <ul>/<li> tags with anchor links. Any markup mistake would render incorrectly or silently break the page.
Method 2 — Custom JavaScript: A developer would use insertAdjacentHTML to inject the menu into the footer element. More powerful, but far riskier — a single syntax error could break the entire page.
What was wrong with this
  • Required HTML or JavaScript knowledge — non-technical users were completely locked out
  • No validation — broken code went live instantly with no warning or easy rollback
  • Updating a single link meant re-opening and editing raw code every time
  • Clients with hundreds of properties had no shared approach — each site was maintained separately
Why this was a real risk
  • Both methods had no safeguards — broken code was saved and published instantly to client-facing sites.
  • Any visual break affects client trust and team credibility. Only designers or developers could fix it, meaning even a small change required escalation and wait time.
  • As the number of properties grew, so did the time cost and risk of error.
How Might We

How might we let anyone on the team — not just designers and developers — create, manage, and publish custom navigation menus for property websites, without ever touching a single line of code?

Key Use Case — Company-Level Menus

One menu, hundreds of properties

A common real-world scenario: a client manages 100+ properties and needs the same set of links — Terms & Conditions, Accessibility Statement, a shared contact page — to appear on every website. Before, this meant updating each property manually.

With Additional Menus, the team creates one menu at the company level. It is then called on each property website using the Site Link Widget in the Site Editor — no duplication, no per-property code, and any future updates flow to all properties automatically.

Step 1 — Create at Company Level
Navigate to Company Configuration → Additional Menus. Select or enter the company ID, then create a new menu (e.g. "Common Links") with all shared URLs the client wants across every property.
Step 2 — Publish Once
Click Publish Changes. The menu is now saved at the company level and made available as a widget across all properties under that client — no need to recreate it per site.
Step 3 — Call it on Any Property via Site Link Widget
Open the Site Editor for any property. Add the Site Link Widget, select the company-level menu, choose orientation, and click Update. The same menu appears live on that property's website.
Step 4 — Update Once, Reflect Everywhere
When a shared URL needs to change, update it once in the company-level menu and republish. Every property that uses this menu reflects the change — no per-property editing required.

Design Constraints

Limits we had to work within

Must live inside the existing configuration panel

The feature had to fit inside the current Site Manager structure — under Company Configuration — without introducing new navigation patterns users would need to learn.

Must be safe for non-technical users

Client success managers also use this platform. The entire flow had to be visual and form-based — no code editor, no raw markup, no technical steps of any kind.

Must connect to the existing Site Editor (CMS)

Created menus needed to surface as widgets in the Site Editor so they could be placed on any page like any other component — without bypassing the existing CMS workflow.

Who We Designed For

Three types of users, one shared need

Designer
Needs to add custom navigation links to a property website without spending time writing and maintaining raw HTML code. Wants a visual tool that is fast and error-free.
Client Success Manager
Manages property accounts and often needs to add or update links like Floor Plans or Terms pages. Cannot write code — needs full independence to make these updates without waiting for a developer.
Developer
Used to be the only person who could add menus via code injection. Wants to hand this task off entirely so they can focus on real development work instead of repetitive content updates.

Feature Walkthrough — Step by Step

How the feature works — from configuration to live website

The screenshots below show the full end-to-end experience — from navigating to Additional Menus in the configuration panel, all the way to seeing the menu appear live on the property website.

Complete walkthrough: Each step in the configuration panel is shown — navigating to Additional Menus, creating a menu, naming it, adding pages and custom links, publishing, placing the widget in the Site Editor, and the final live output on the property website footer.
Step 1 — Navigate to Additional Menus
Go to Company Configuration in the Site Manager panel. Select the company using a company ID or client ID. Then click on Additional Menus in the left navigation. From here you can create a new menu or select an existing one to edit.
Step 2 — Create a new menu
Click Create New Menu. A dialog appears asking you to enter a menu name. Type the name (for example, "Your Menu") and confirm. The new menu is immediately added to the dropdown list and ready to edit.
Step 3 — Add pages and custom links
After selecting your menu, you can add existing pages from the site (like Floor Plans or Contact) or add custom links with any URL you choose. Both options are available in the same editor. You can also sort items to control the order in which they appear.
Step 4 — Publish changes
Once you are happy with the menu, click Publish Changes. This saves and activates the menu, making it available as a widget inside the Site Editor (CMS). Nothing appears on the website yet — you still need to place the widget on a page.
Step 5 — Place the menu in the Site Editor
Open the Site Editor. Navigate to the location where the menu should appear (for example, the footer). Find the Site Link Widget in the widget section. Select the menu you created, choose the orientation (vertical or horizontal), then click Update.
Step 6 — Menu is live on the website
After updating, the menu is now visible on the live website. All the links appear exactly as configured — no code involved at any step. To update the menu later, simply go back to Additional Menus, make changes, and publish again.

Before & After

What changed for the team

Before
  • No built-in feature — menus required custom HTML or JavaScript written by hand
  • Only designers and developers could create or update menus; non-technical users had to wait
  • A single typo in code went live immediately and could break the client's website
  • Clients with 100+ properties had to maintain menus separately on every site — no company-level sharing
  • Every small change (adding a link, reordering) meant re-opening raw code
After
  • Dedicated Additional Menus section in Company Configuration — zero code required
  • Anyone on the team — designer, developer, or client success manager — can create and manage menus independently
  • Form-based input eliminates the risk of broken markup going live
  • Company-level menus can be created once and applied across all properties via the Site Link Widget
  • Links can be sorted, updated, or removed anytime through a simple visual interface

Key Design Decisions

Why each part was built this way

Every decision came from a clear problem. Nothing was added just to look complete — each feature directly replaced a painful manual step from the old process.

Form-based editor Instead of a code editor or HTML textarea, menu items are added through simple input fields — a label and a URL. This makes the feature accessible to anyone on the team, not just people who know HTML.
Existing pages + custom links Users can add existing site pages directly from a dropdown (no need to know or type the URL manually) and can also add custom external links. Both needs are covered in one place without switching tools.
Named menus with a dropdown Each menu gets a name and lives in a dropdown list. Multiple menus can be created for different purposes — footer links, sidebar navigation, etc. — and each one is managed independently without interfering with the others.
Sorting and reordering Menu items can be dragged to reorder them. Before, changing the order of links meant editing the raw HTML and counting list items manually. Now it takes a few seconds with no risk of errors.
Publish before placement Publishing the menu in the configuration panel and placing it in the Site Editor are two separate steps. This gives teams flexibility — a menu can be fully built and ready before it is placed on any page. Changes can be made without touching the live layout.
Orientation choice in the widget When placing the menu in the Site Editor, the user can choose vertical or horizontal orientation. This removes the need to adjust CSS manually to change how the menu displays on the page.

Edge Cases

Situations we accounted for

A newly created menu appears in the dropdown immediately after naming — no page refresh needed. Users can start adding items right away.
Selecting an existing menu loads all previously added items instantly, so users continue where they left off.
A menu can be deleted entirely from the dropdown if no longer needed — without affecting any other menus or touching code.
A published but unplaced menu does not appear on the live site — it is available but inactive until a widget is placed in the Site Editor.
Company-level menus can be placed on multiple properties simultaneously — each property's Site Editor independently calls the same menu via the Site Link Widget.
Design Principle — Accessibility Over Power
  • The goal was not to replicate the full power of code — it was to cover all real-world needs in a way anyone can use safely.
  • Form fields replace raw HTML. A publish button replaces a code deployment. A widget replaces a script injection. Every step is visual, guided, and reversible.
  • The two-step process — configure then place — gives teams a safe buffer between building a menu and making it visible on the live site.

Trade-offs

What we gained and what we accepted

What we gained
  • Anyone can create and manage menus — no technical knowledge needed
  • Zero risk of breaking a live site through a code mistake
  • Sorting, updating, and deleting items takes seconds instead of minutes
  • The dependency on designers and developers for menu management is fully removed
What we accepted
  • The feature supports standard navigation links only — highly customised HTML menus with special markup still require a developer
  • The two-step publish and placement process means menus are not instantly live — there is a deliberate extra step before they appear on the site
  • Advanced styling options (colours, fonts, spacing) are controlled by the Site Editor widget, not the menu builder itself
Why it was worth it
  • The vast majority of additional menu needs are standard navigation links — this feature covers nearly all real-world use cases
  • The deliberate publish step prevents accidental changes from going live — the slight delay is a safety feature, not a drawback
  • Removing developer dependency for routine menu tasks creates measurable time savings across the whole team
What could be better next
  • Add a live preview of the menu inside the configuration panel before publishing
  • Allow sub-menu or nested link support for properties that need multi-level navigation
  • Show which pages the menu is currently placed on, directly from the configuration view

Learnings

What I learned from this project

01
Removing dependency is a feature in itself. The most valuable outcome of this project was not the interface — it was the independence it gave to non-technical users. When people can do their job without waiting for someone else, everything moves faster and with less friction.
02
Replacing code with a form is not simplification — it is accessibility. The feature does not do less than the old code-based method. It does the same thing, but in a way that any user can access and use safely. Accessibility and power are not opposites.
03
A two-step publish process builds confidence, not friction. Separating "build the menu" from "place the menu on the page" felt like extra work at first. But it gives users control and safety — they can prepare something without it going live until they are ready.
04
The best features solve a real operational pain, not just a UX problem. This was not just about making something easier to use. It solved a genuine operational problem — risk, dependency, and time cost — that affected the whole team. That made the case for building it very clear.
05
When the old way requires technical knowledge, expanding access is the goal. Many internal tools are built for power users first. But when a task is routine and the only barrier is technical know-how, the right design decision is to remove that barrier entirely — not work around it.
